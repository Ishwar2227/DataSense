# DataSense — Question Answering Architecture

## 1. Purpose

This document describes how DataSense handles natural-language business questions through the **Ask Data** feature.

The design separates:

1. question understanding
2. deterministic statistical analysis
3. language generation

This allows the system to provide natural-language answers while keeping the underlying business numbers grounded in computed data.

---

## 2. High-Level Flow

The current question-answering flow is:

```text
User Question
     |
     v
Question Intent Detection
     |
     +---- unsupported ----> Safe Fallback
     |
     v
Deterministic Analysis
     |
     v
Question-Specific Statistics
     |
     v
Trusted Data Prompt
     |
     v
Groq LLM
     |
     v
Natural-Language Answer
```

The LLM is therefore not responsible for discovering the raw dataset statistics from scratch.

---

## 3. Supported Question Intents

The current implementation maps natural-language questions to a small set of fixed intents.

### 3.1 Why Change

Examples:

- Why did sales fall?
- Why did revenue change?
- What caused the change in value?

This intent uses the latest and previous available periods.

The statistics include:

- date column
- value column
- latest period
- previous period
- latest value
- previous value
- absolute change
- percentage change

---

### 3.2 Top Group

Examples:

- Which region changed the most?
- Which category contributed most to the change?
- Which group grew the most?

This intent compares group-level values between the latest and previous periods.

The statistics include:

- group column
- value column
- latest period
- previous period
- group
- change
- percentage change

---

### 3.3 Anomalies

Examples:

- Are there unusual sales values?
- Are there anomalies?
- Which values look unusual?

This intent uses the deterministic anomaly-detection output.

The current anomaly rule is based on:

```text
|Z| >= 3
```

The statistics include:

- value column
- outlier count
- relevant outlier records

---

## 4. Intent Detection

The question-intent layer maps phrases and keywords to supported analytical operations.

Conceptually:

```text
question
   |
   +--> change / sales fall / value change
   |        |
   |        v
   |     why_change
   |
   +--> region / category / group change
   |        |
   |        v
   |     top_group
   |
   +--> unusual / anomaly / outlier
            |
            v
         anomalies
```

If the system cannot confidently map the question to one of the supported intents, the question is treated as unsupported.

---

## 5. Unsupported Questions

DataSense does not attempt to answer every possible business question.

For example, questions requiring functionality that is not currently implemented can return a safe fallback.

Example:

```text
This question type is not currently supported.
```

This prevents the system from pretending to have performed an analysis that does not exist.

---

## 6. Deterministic Statistics Before the LLM

Once an intent is identified, DataSense obtains the statistics required for that intent.

For example, for a month-over-month change:

```text
Latest value     = 433,668.01
Previous value   = 1,461,756.25
Change           = -1,028,088.24
Change %         = -70.33%
```

These values are calculated by the analysis pipeline rather than generated by the LLM.

The LLM receives these trusted statistics as input.

---

## 7. Why the LLM Does Not Calculate the Numbers

The LLM is used for language generation rather than primary statistical computation.

This separation reduces the risk of:

- arithmetic mistakes
- hallucinated values
- unsupported calculations
- inconsistent answers

The deterministic layer remains responsible for the actual numerical analysis.

---

## 8. Trusted-Data Prompt

The question-answering layer constructs a prompt containing only the relevant statistics for the selected intent.

The prompt instructs the model to:

- use only the supplied facts
- preserve the supplied numbers
- avoid inventing causes
- avoid unsupported explanations
- state when the data does not establish a reason
- answer concisely and professionally

The intended behavior is:

```text
Computed statistics
       |
       v
Trusted-data prompt
       |
       v
LLM explanation
```

rather than:

```text
Raw CSV
   |
   v
LLM guesses what happened
```

---

## 9. No Fabricated Causal Explanations

A decrease in sales does not automatically establish why the decrease happened.

For example, if the data only shows:

```text
November: 1,461,756.25
December:   433,668.01
Change:   -1,028,088.24 (-70.33%)
```

DataSense can report the change.

It should not automatically claim that the decrease was caused by:

- customer behavior
- competition
- pricing
- promotions
- seasonality

unless the supplied analysis actually supports that explanation.

The system therefore distinguishes between:

**Observed fact**

> Sales decreased by the computed amount.

and:

**Unsupported causal claim**

> Customers stopped buying because of a competitor.

Only the first type is guaranteed by the current analysis.

---

## 10. Missing-Data Fallbacks

Some intents require specific fields.

For example, a month-over-month question requires usable date information.

If a dataset has no usable date column, DataSense returns a limitation instead of inventing a time period.

Example:

```text
This analysis is unavailable because no usable date column was detected.
```

Similarly, if the required value or group information is unavailable, the corresponding analysis is marked unavailable.

---

## 11. Dataset-Specific Question Statistics

The question-answering layer uses the statistics already computed for the uploaded dataset.

This avoids repeatedly rediscovering:

- the date column
- the value column
- the group column
- the latest period
- the previous period

The analysis response contains a `question_stats` structure used by the question endpoint.

---

## 12. Question Caching

Question results are cached based on the uploaded dataset and question context.

### Purpose

Large datasets can require substantial processing time on the first analysis.

Repeated questions should not need to repeat the same expensive computation.

### Flow

```text
First question
     |
     v
Analyze dataset
     |
     v
Generate statistics
     |
     v
Generate answer
     |
     v
Cache result

Repeated question
     |
     v
Cache lookup
     |
     v
Return cached result
```

This significantly reduces response time for repeated questions.

---

## 13. Large Dataset Behavior

DataSense has been tested with datasets ranging from small CSV files to datasets containing millions of rows.

The question-answering architecture is designed so that:

- expensive deterministic analysis happens once
- question-specific statistics are reused
- repeated questions can use cached results
- the LLM receives only relevant statistics instead of the entire CSV

This keeps the LLM prompt smaller and reduces unnecessary model processing.

---

## 14. Outlier Data Handling

For anomaly questions, the system can identify relevant outlier records before sending information to the LLM.

This prevents the model from needing to inspect the entire dataset to determine which values are anomalous.

The deterministic analysis layer is responsible for identifying the outliers.

The LLM is responsible only for expressing the result in natural language.

---

## 15. Groq Integration

The current implementation uses the Groq API for language generation.

The configured model is:

```text
openai/gpt-oss-20b
```

The model is configured with a low temperature to encourage consistent responses.

The current generation is also constrained by a maximum completion-token limit so answers remain concise.

---

## 16. API Boundary

The frontend sends a question request to:

```text
POST /api/question
```

The request contains the uploaded dataset context and the user's question/intent information required by the backend.

The backend:

1. validates the request
2. identifies the question intent
3. obtains the required statistics
4. checks whether the analysis is available
5. creates a trusted-data prompt
6. calls the LLM when appropriate
7. returns the answer and supporting question information

---

## 17. Response Structure

The question endpoint returns information including:

- question
- question ID
- selected statistics
- generated answer

This allows the frontend to display the natural-language response while retaining the structured analytical context.

---

## 18. Frontend Ask Data Flow

The frontend workflow is:

```text
User types question
        |
        v
Ask Data request
        |
        v
Backend question endpoint
        |
        v
Intent + statistics + LLM
        |
        v
Answer
        |
        v
Displayed in Ask Data panel
```

The frontend does not perform the core business calculations.

---

## 19. Error and Failure Handling

The system handles several failure categories separately.

### Unsupported Question

```text
This question type is not currently supported.
```

### Missing Required Data

```text
This analysis is unavailable because the required column was not detected.
```

### Missing LLM Configuration

The backend validates that the required Groq API configuration exists before attempting model generation.

### General Request Failure

The frontend displays an error state rather than silently presenting an incomplete answer.

---

## 20. Grounding Principle

The central design principle is:

> **The LLM explains computed facts; it does not become the source of those facts.**

This is important because DataSense is intended to answer business questions using uploaded data.

The numerical source of truth remains the deterministic analysis pipeline.

---

## 21. Current Limitations

The current question-answering system does not provide unrestricted natural-language data analysis.

Current limitations include:

- only a fixed set of question intents is supported
- causal analysis is limited
- arbitrary multi-step analytical questions are not yet supported
- the LLM cannot safely answer questions when the required statistics are unavailable
- broader open-ended querying is future work

These limitations are intentional in the current phase.

The fixed-intent approach provides a controlled foundation before expanding to more open-ended analytical questions.
